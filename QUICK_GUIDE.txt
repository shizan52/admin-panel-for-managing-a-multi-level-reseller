PROJECT OVERVIEW
----------------
This is a Flask-based dashboard system with role-based access control and 
messaging/inbox functionality. Four user roles exist: Master, Admin, 
Super Seller, and Seller.


GETTING STARTED
---------------

1. START THE SERVER
   Open PowerShell in project folder and run:
   
   python app.py
   
   Server will start at: http://localhost:5000 or http://127.0.0.1:5000


2. OPEN IN BROWSER
   Navigate to: http://localhost:5000
   You will be redirected to the login page automatically.

KEYS SYSTEM (ACCESS TOKENS) - HOW IT WORKS
-------------------------------------------

PURPOSE:
Keys are access tokens (API/license keys) created and managed by users (mainly sellers). Each key has a name, password (for authentication), a unique 9-digit code, and status (active/inactive). Only one device (IP address) can use a key at a time. Paid status (set by higher role) enables 30-day active duration.

ROLE-BASED ACCESS:
- Seller: Can create/manage own keys (create, view, reset device, delete). Cannot set paid/active duration. Keys created unpaid.
- Super Seller: Can manage sellers' keys, set paid (activate for 30 days). Own keys created unpaid.
- Admin: Can manage super sellers' keys, set paid. Own keys created unpaid.
- Master: Can manage all keys, set paid. **Own keys auto-activated for 30 days** (master privilege).
- Hierarchy: Higher roles can view/manage lower roles' keys, never the reverse.

DATABASE STRUCTURE:
- keys table: id, name (unique per creator), key_code (unique 9-digit), password_hash (bcrypt), created_by (FK to users.id), created_at, active_until (date), is_paid (bool), is_active (bool, computed from active_until).
- key_access table: id, key_id (FK), ip_address, last_access. Only one device per key enforced.

KEY CREATION FLOW:
1. Sidebar: "Create Key" link loads form (name, password, confirm password).
2. User fills form → JS validates → POST /api/keys/create {name, password}.
3. Backend: 
   - Checks login/role, name uniqueness, hashes password, generates unique 9-digit key_code
   - If role=master: Sets is_paid=1, is_active=1, active_until=today+30days (auto-activated)
   - If role≠master: Sets is_paid=0, is_active=0, active_until=NULL (needs activation)
4. Success: Returns {success, key_code, is_paid, is_active, active_until, message}. JS shows key_code with special message for master.
5. Edge: Duplicate name → error. Key_code collision (rare) → regenerate.

MANAGE/ALL KEYS FLOW:
1. Sidebar: "Manage Keys" loads table of keys (name, code, status, duration, created, IP, actions).
2. Table: Shows only own/subordinate keys (role-based filter). Columns: Name, Key Code, Active Duration (days left or Inactive), Status (active/inactive), Created At, IP.
3. Actions:
   - Activate: Higher role can activate unpaid key (PUT /api/keys/update-paid/<key_id> with is_paid=true), sets active_until, is_active.
   - Extend: Higher role can extend EXISTING active key's validity (PUT /api/keys/update-paid/<key_id> with extend=true). Adds days to current expiry.
   - Unpay: Higher role can deactivate key (PUT /api/keys/update-paid/<key_id> with is_paid=false).
   - Reset Device: Creator or higher can reset device lock (POST /api/keys/reset-device/<key_id>).
   - Delete: Delete key (DELETE /api/keys/delete/<key_id>), cascades to key_access and key_access_history.
4. Device Restriction: On key access, IP is checked/set. If device mismatch, access is blocked unless reset.
5. Expiry: If active_until < today, is_active=false (auto-computed on load).

ERROR HANDLING & SECURITY:
- Unauthorized access: 403. Invalid input: 400. DB error: 500. JS shows errors/alerts.
- Passwords always hashed (bcrypt). Key_code never editable. All inputs sanitized.
- One device per key enforced (key_access unique per key_id).

INTEGRATION:
- Backend: New API routes in app.py (see below). Uses session for auth, role checks, and hierarchy enforcement.
- Frontend: Sidebar links for "Create Key" and "Manage Keys". Form/table generated by keys.js. All actions via API.
- JS: keys.js handles all UI, fetches, and updates dynamically.

API ENDPOINTS (KEYS):
- POST   /api/keys/create            - Create new key
- GET    /api/keys/list              - List keys (role-based)
- PUT    /api/keys/update-paid/<id>  - Set/extend paid/active status (params: is_paid, duration_days, extend)
- POST   /api/keys/reset-device/<id> - Reset device IP
- DELETE /api/keys/delete/<id>       - Delete key
- POST   /api/keys/access            - Validate key access (for external apps)
- GET    /api/keys/access-history/<id> - Get access history for a key
- POST   /api/keys/access/<code>    - Access key (IP/MAC check, password verify)

UI/UX:
- Sidebar: "Create Key", "Manage Keys" for all roles.
- Create Key: Form with name, password, confirm. On success, shows generated key_code.
- Manage Keys: Table with all info, action buttons (Set Paid, Reset IP/MAC, Delete) as per permissions.
- All actions update UI in real time.

TYPICAL WORKFLOW:
1. Seller creates key → gets code → uses on device (locks to IP/MAC).
2. Super Seller/Admin/Master can activate (paid) for 30 days.
3. If device changes, must reset IP/MAC via UI.
4. Expired/unpaid keys auto-inactive.
5. All actions logged and validated by backend.

TROUBLESHOOTING
---------------

Problem: Cannot login
Solution: 
  - Check username and password are correct
  - Ensure login type matches user role
  - Check server is running (python app.py)

Problem: Sign out not working
Solution:
  - Hard refresh browser (Ctrl + Shift + R)
  - Clear browser cache
  - Restart server

Problem: Inbox not loading
Solution:
  - Check browser console for errors (F12)
  - Verify server is running
  - Refresh the page
  - Check database file exists (venom_users.db)

Problem: Cannot send message
Solution:
  - Verify you have permission to message that role
  - Check recipient exists in dropdown
  - Ensure all fields are filled
  - Check browser console for errors

Problem: Compose button not showing
Solution:
  - This is normal for Sellers (they cannot send messages)
  - Check your role permissions

KEY MANAGEMENT SYSTEM - HOW IT WORKS
-------------------------------------

WHAT IS A KEY?
A key is an access token with:
- Unique 9-digit code (randomly generated)
- Name (identifier set by creator)
- Password (for authentication)
- Status (Active/Inactive based on paid status)
- Device binding (one key = one device via IP/MAC)

ROLE HIERARCHY & KEY PERMISSIONS:

Master
├─ Can create/manage keys
├─ Can activate keys (set paid status)
└─ Can view all admin/super_seller/seller keys

Admin
├─ Can create/manage keys
├─ Can activate keys (set paid status)
└─ Can view super_seller/seller keys

Super Seller
├─ Can create/manage keys
├─ Can activate keys (set paid status for seller keys)
└─ Can view seller keys

Seller
├─ Can create own keys
├─ Can view/delete own keys
├─ Can reset own key device
└─ CANNOT activate keys (needs super_seller approval)

KEY FEATURES:

1. CREATE KEY
   - Menu: "Create Key" in sidebar
   - Required: Name (min 3 chars), Password (min 6 chars)
   - System generates unique 9-digit code
   - Initially inactive (unpaid)

2. VIEW ALL KEYS
   - Menu: "All Keys" in sidebar
   - Shows: Name, Code, Creator, Status, Duration, Device, Actions
   - Search by name or key code
   - Filter by status (Active/Inactive/All)
   - Higher roles see subordinate keys

3. ACTIVATE KEY (Paid Status)
   - Only higher roles can activate
   - Select duration: 7/15/30/60/90 days
   - Click "✅ Activate" button
   - Sets active duration
   - Key becomes usable
   - Click "❌ Unpay" to deactivate

4. KEY ACCESS & AUTHENTICATION
   - Use endpoint: POST /api/keys/access
   - Send: {key_code, password}
   - Returns: Access granted/denied
   - First access records device IP
   - Subsequent access validates IP match
   - Blocks different device automatically

5. DEVICE BINDING
   - First login from device records IP/MAC
   - Same key cannot be used from different device
   - "🔄 Reset" button removes device binding
   - Allows new device login

5. DELETE KEY
   - Creator or higher role can delete
   - "🗑️ Delete" button with confirmation
   - Permanently removes key


KEY STATUS EXPLAINED:

Active (Green)
- Paid status enabled
- Has valid duration (days remaining shown)
- Can be used for authentication

Inactive (Red)
- Not paid OR duration expired
- Cannot be used
- Needs activation by higher role
